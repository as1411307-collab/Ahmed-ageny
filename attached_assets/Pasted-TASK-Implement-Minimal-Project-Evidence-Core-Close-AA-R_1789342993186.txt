==================================================
1. Project Evidence Core
==================================================

أنشئ Core داخلي موحد مسؤول فقط عن:

- safe project reads
- path policy
- hashing
- provenance
- evidence extraction contract

ولا تجعله Agent Tool عامًا.

يجب ألا يستطيع الموديل تمرير arbitrary filesystem path إلى الـCore مباشرة.


--------------------------------
1.1 Access Mode
--------------------------------

Read-only فقط.

ممنوع:

- write
- rename
- delete
- chmod
- shell execution
- subprocess execution
- network access
- package installation
- deploy/publish
- secret retrieval
- arbitrary repository browsing بواسطة الموديل


--------------------------------
1.2 Repository Boundary
--------------------------------

كل path يجب:

1. يبدأ من project root المعروف.
2. يمر عبر resolve/canonicalization.
3. يبقى داخل project root بعد resolve.
4. يرفض symlink يؤدي خارج project root.
5. يمر عبر allowlist.
6. يمر أيضًا عبر deny rules.

منع path traversal مثل:

../
../../
absolute paths
encoded traversal forms إذا كانت طبقة الإدخال تسمح بها.


--------------------------------
1.3 Global Read Allowlist
--------------------------------

اسمح مبدئيًا فقط بمناطق source/config/documentation المناسبة:

- src/ إذا كانت موجودة فعليًا
- config/ إذا كانت موجودة
- ملفات Python source ذات الصلة داخل بنية المشروع الفعلية
- package.json إذا وجد
- pyproject.toml إذا وجد
- requirements.txt إذا وجد
- docs/ إذا وجدت
- ADR/ إذا وجدت

لكن:

وجود المسار في global allowlist لا يعني أن كل Capability تستطيع قراءته.

يجب وجود Capability-Specific Allowlist أيضًا.


--------------------------------
1.4 Explicit Deny
--------------------------------

ارفض دائمًا:

- .env
- .env.*
- .git/
- private keys
- SSH keys
- credential stores
- secret files
- auth tokens
- service account credential payloads
- node_modules/
- __pycache__/
- build/
- dist/
- temporary caches
- generated runtime caches
- أي path خارج project root

لا تعرض secret values حتى لو ظهر reference إليها داخل source.

مسموح فقط بإظهار اسم configuration key أو environment variable إذا كان ذلك ضروريًا لإثبات wiring، مثال:

GOOGLE_API_KEY referenced = true

لكن:

GOOGLE_API_KEY value = ممنوع.


==================================================
2. Evidence Contract
==================================================

أنشئ contract واضحًا شبيهًا بالتالي، باستخدام نمط المشروع الحالي إن كان Pydantic مستخدمًا بالفعل.

لا تضف dependency جديدة لمجرد هذا schema إذا كان يمكن تنفيذه بما هو موجود.

المفهوم المطلوب:

EvidenceStatus:
- VERIFIED
- NOT_FOUND
- DISCREPANCY
- DENIED

ProjectEvidenceEnvelope يحتوي على الأقل:

- schema_version
- capability_name
- query_id أو inspection_id
- target/component identifier
- evidence_status
- extracted_facts
- provenance_metadata
- inspection_timestamp

ولكل evidence item:

- relative source path
- file SHA-256
- line أو line range إن أمكن
- extracted evidence
- trust classification
- verification status

لا تُرجع الملف كاملًا إذا كانت facts المطلوبة تكفي.

لا تجعل summary النصي هو مصدر الحقيقة.
الحقائق المنظمة + provenance هي الأساس.


==================================================
3. Hashing & Provenance
==================================================

لكل ملف تتم قراءته:

- احسب SHA-256 من bytes الفعلية.
- سجل relative path فقط.
- سجل evidence lines/ranges.
- سجل file hash مع fact الذي استُخرج منه.

لا تعتبر hash دليلًا على صحة المعنى.
هو دليل integrity/provenance فقط.

يجب أن يكون واضحًا الفرق بين:

- source exists
- configuration declaration exists
- runtime wiring exists
- component is actually operational

لا تستنتج operational لمجرد وجود class أو file.

==================================================
6. ما الذي يجب أن تفحصه inspect_source_status؟
==================================================

لكل component مستهدف استخرج بشكل مستقل:

1. implementation evidence
   - هل implementation موجود؟
   - أين؟
   - ما file hash؟

2. registration/wiring evidence
   - هل component مربوط فعليًا بالنظام؟
   - أم مجرد كود غير مستخدم؟

3. configuration declaration
   - ما config keys المطلوبة؟
   - هل التعريف موجود؟
   - لا تقرأ secret values.

4. setup/readiness evidence
   - هل المتطلبات البرمجية/configuration wiring موجودة؟
   - هل توجد dependencies المطلوبة؟

5. contradictions
   - implementation موجود لكن غير مربوط.
   - config متوقع وغير موجود.
   - أكثر من implementation متعارض.
   - legacy implementation موجود بجانب active implementation.

6. evidence limitations
   - ما الذي يمكن إثباته من source/config؟
   - وما الذي لا يمكن إثباته بدون external/live check؟

مهم جدًا:

لا تستخدم كلمة operational إلا إذا كان الدليل الفعلي يبررها.

إذا كان الموجود يثبت فقط أن component:
- implemented
- registered
- configured-by-declaration

قل ذلك صراحة.

External provider health أو secret validity ليست جزءًا من هذه capability.


==================================================
7. Decision Semantics
==================================================

استخدم القواعد التالية:

VERIFIED:
الدليل المطلوب لهذه claim موجود ومتسق ضمن scope الأداة.

NOT_FOUND:
المكوّن أو الدليل المطلوب غير موجود ضمن المناطق المسموح بها.

DISCREPANCY:
هناك source/config/wiring متعارض أو ناقص يجعل الادعاء المقصود غير صحيح أو غير مكتمل.

DENIED:
الدليل المطلوب يقع خارج boundary المسموح بها أو داخل secret/denied area.

ممنوع التخمين.

ممنوع تحويل NOT_FOUND إلى VERIFIED من الذاكرة أو documentation فقط.
