المرحلة التالية: Evaluation Baseline

الهدف ليس تقييم “هل الرد جميل؟”، بل قياس أربع طبقات منفصلة:

المجال	ما نقيسه	لماذا مهم
Retrieval	هل وجد المصدر الصحيح؟	يمنع تحسين الإجابة فوق سياق خاطئ
Grounding	هل الجواب مبني فعليًا على المصدر؟	يمنع الهلوسة
Tool selection	هل استخدم الأداة الصحيحة وفي الوقت الصحيح؟	يقيس سلوك الوكيل
Task completion	هل أنجز المطلوب كاملًا؟	المقياس النهائي

وأضيف معها مقاييس تشغيلية ثانوية:

latency, tool_calls, tokens/cost, retries.

أهم قرار في تصميم الـEvals

لا تبنِ dataset اصطناعية فقط.

الأفضل تكون أغلب الحالات من أسئلتك الحقيقية السابقة، خصوصًا الحالات التي سببت لنا لخبطة فعلًا:

* قرار حديث يناقض قرارًا قديمًا.
* البحث داخل ملفات المشروع.
* الفرق بين معلومة مؤكدة ومسودة.
* متى يستخدم WEB ومتى MY_FILES.
* متى يحتاج HITL.
* سؤال لا توجد له معلومات كافية.
* استخدام مصدر حديث مقابل مصدر قديم.
* استرجاع قرار سابق من مشروع Ahmed Agent.
* سؤال متعدد الخطوات.
* تصحيح المستخدم لمعلومة سبق حفظها.

هذه الحالات ستكشف جودة النظام أكثر من benchmark عام.

لا تبدأ بـ100 حالة

ابدأ بمجموعة صغيرة قوية، تقريبًا 20–30 حالة، موزعة على الأنماط المهمة.

كل case يحتاج على الأقل:

id
category
input
expected_behavior
expected_sources
forbidden_behavior
required_tools
success_criteria

ولا أنصح أن يكون التقييم كله LLM judge.

استخدم:

Deterministic checks عندما يمكن التحقق آليًا:

* هل استخدم tool المطلوب؟
* هل استخدم مصدرًا ممنوعًا؟
* هل citation موجود؟
* هل خرج schema صحيح؟
* هل استدعى action حساس بدون approval؟

ثم model grader للحاجات الدلالية:

* groundedness
* relevance
* completeness
* source correctness

ترتيب العمل داخل Evaluation

1. Freeze baseline الحالي
    المتطلبات: commit/version ثابت + model/config المستخدمة.
    الوقت: قصير.
    النتيجة: نقطة مقارنة قابلة للإعادة.
2. بناء eval dataset من الحالات الحقيقية
    المتطلبات: 20–30 حالة متنوعة.
    الوقت: متوسط.
    النتيجة: benchmark يمثل استخدامك فعليًا.
3. إضافة deterministic graders
    المتطلبات: tool traces + citations + run metadata.
    الوقت: متوسط.
    النتيجة: قياسات موضوعية.
4. إضافة semantic graders
    المتطلبات: rubric واضح لكل معيار.
    الوقت: متوسط.
    النتيجة: groundedness/completeness قابلة للقياس.
5. تشغيل baseline الحالي بدون أي تعديل Memory/Retrieval
    النتيجة: أول scoreboard حقيقي لـAhmed Agent.

وبعدها فقط نبدأ Context + Memory Architecture ونشغّل نفس الـevals مرة ثانية.

لو تحسن:
نستمر.

لو تراجع:
نعرف تحديدًا أي metric تدهورت.

ده هو الفرق بين تطوير Agent بالتجربة وبين تطويره كنظام هندسي.

الخلاصة: لا تضف Memory الآن. ثبّت baseline، وابنِ Evaluation Harness أولًا. وبعد أول نتيجة سنعرف فعلًا أين عنق الزجاجة: retrieval، grounding، tool selection، أو context.
