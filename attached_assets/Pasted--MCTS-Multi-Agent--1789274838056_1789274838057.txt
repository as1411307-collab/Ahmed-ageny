المسار المطبّق صحيح، لكن الخطوة التالية ليست MCTS ولا Multi-Agent ولا حتى سياسة الاحتفاظ؛ الأولوية الآن هي تحويل الـ checkpoints من سجل مراقبة إلى آلية استرداد فعلية بعد الأعطال.

حاليًا Ahmed Agent أصبح عنده طبقة تشغيل أقوى: حالة حتمية، persistence، audit trail، وفحص لكل Run. لكن هناك فرق مهم بين:

«أعرف أين توقف التنفيذ»

وبين:

«أستطيع استئناف التنفيذ بأمان من المكان الذي توقف فيه».

وهذه هي الفجوة الأهم الآن.

الخيار	الميزة	العيب / المخاطرة	الوقت والجهد	الترشيح والسبب
Recovery + Resume	يجعل checkpoints مفيدة فعليًا ويقاوم restart/crash	يحتاج ضبط idempotency بعناية	متوسط	الأولوية 1
سياسة retention للـ checkpoints	تمنع تضخم PostgreSQL	لا تحسن قدرة الوكيل نفسها	منخفض	أولوية 3

الخطوة التي أرشحها الآن: Run Recovery

المطلوب ليس بناء نظام جديد، بل إكمال نفس المعمارية:

1. اكتشاف التنفيذات المعلّقة بعد restart

مثل Run بقي:

model_running

ثم مات السيرفر.

عند بدء Ahmed Agent مرة أخرى يجب تحديد أن هذا التنفيذ stale/orphaned، بدل أن يبقى إلى الأبد وكأنه ما زال يعمل.

2. تعريف سياسة واضحة لكل حالة

مثلاً:

* created → يمكن إعادة التشغيل.
* context_loaded → يمكن استئناف التنفيذ.
* model_running → لا يعاد الطلب بشكل أعمى؛ يجب تحديد هل العملية ماتت أم ما زالت مملوكة لعامل آخر.
* response_ready → يحفظ الرد بدل إعادة استدعاء النموذج.
* response_persisted → يكمل إلى completed.
* failed → يبقى terminal إلا من خلال Run جديد أو retry صريح.

وهذا يحافظ على المبدأ الذي بنيته الآن: لا تخطي للمراحل ولا انتقالات عشوائية.

3. Idempotency

هذه أهم نقطة تقنيًا.

إذا حصل crash بعد تنفيذ Tool ولكن قبل تسجيل checkpoint، فلا يصح أن يؤدي Resume إلى تنفيذ نفس الفعل مرتين.

بالتالي أي Tool قد ينتج side effect يحتاج على الأقل:

run_id + step_id/idempotency_key

حتى لا يتحول recovery نفسه إلى مصدر مشاكل.

4. Lease / execution ownership

حتى لا يشغّل عاملان نفس الـ Run معًا:

* worker_id
* lease_expires_at
* claim/renew/release

بدون هذا، checkpointing وحده لا يمنع duplicate execution عند التوسع أو restart غير النظيف.

5. اختبار الأعطال الحقيقي

الـ 51/51 ممتازة كاختبارات برمجية، لكن الاختبار المهم التالي يجب أن يكون fault injection:

Start Run
↓
context_loaded
↓
model_running
↓
اقتل العملية
↓
أعد تشغيل السيرفر
↓
اكتشف الـ orphaned run
↓
استعد التنفيذ
↓
لا تكرر أي side effect
↓
completed

إذا نجح هذا السيناريو، وقتها أعتبر طبقة Durable Execution عند Ahmed Agent مكتملة فعليًا.

وبعدها مباشرة

الترتيب الذي أراه الأقوى أصبح:

Durable state ✅ → Recovery/Idempotency → Retention/cleanup → Observability/metrics → Memory quality → تقييم الحاجة إلى orchestration أكثر تطورًا.

وليس:

Durable state → LangGraph → Multi-Agent → MCTS.

النقطة المهمة: لا تغيّروا المعمارية الآن. ما تم بناؤه بدأ يتحول من prototype agent إلى runtime منضبط. إدخال framework orchestration كبير في هذه المرحلة سيضيف abstraction فوق شيء أنتم بالفعل بنيتم أساسه بصورة مناسبة.

الخطوة: Recovery + Resume + Idempotency
المتطلبات: الجداول الحالية للـ runs/checkpoints، transaction locking، worker lease، مفاتيح idempotency.
الوقت والجهد: متوسط؛ تعديل مركز وليس إعادة بناء.
النتيجة: Ahmed Agent ينجو من restart/crash ويكمل التنفيذ دون تكرار العمليات.

بعد إغلاق هذه النقطة، عندنا أساس قوي جدًا نقرر عليه ما إذا كان المشروع يحتاج فعلًا LangGraph أو أن الـ runtime الحالي يكفي.
