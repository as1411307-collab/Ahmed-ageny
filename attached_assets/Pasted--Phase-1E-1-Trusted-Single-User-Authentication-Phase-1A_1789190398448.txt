الـblocker الوحيد:
الخدمة تعتمد على X-Replit-User-Id ويجب إثبات أن هذا الـheader موثوق فقط عندما يأتي من Replit authentication proxy.

الهدف:
تثبيت مصادقة مستخدم واحد فقط — أحمد — بدون بناء نظام multi-user أو RBAC.

1) افحص طريقة Replit authentication الحالية فعليًا.

أريد تقريرًا عن:
- هل التطبيق يعمل خلف Replit Auth؟
- من أين يأتي X-Replit-User-Id؟
- هل يستطيع request مباشر إلى backend تجاوز proxy وحقن header مزيف؟
- هل backend port مكشوف مباشرة أم فقط عبر Replit proxy؟

لا تفترض.

2) TRUST BOUNDARY

اعتبر X-Replit-User-Id موثوقًا فقط إذا ثبت أنه يأتي من Replit proxy الموثوق.

إذا كان backend يمكن الوصول له مباشرة:
- لا تعتمد على header وحده.
- امنع direct unauthenticated backend access أو أضف server-side verification.

3) SINGLE OWNER

لا تبنِ user system.

استخدم Owner واحد فقط.

أضف config مثل:
AHMED_OWNER_USER_ID

المستخدم الموثق يجب أن يطابق هذه الهوية.

إذا الهوية لا تطابق:
403

إذا لا توجد هوية موثوقة:
401

4) DO NOT TRUST CLIENT HEADERS

أي client-supplied identity header يجب ألا يكون كافيًا وحده.

اختبر spoofing صراحة.

5) PROTECT THESE ENDPOINTS

يجب أن تحتاج owner authentication:

/chat/message
/files/upload
/actions/*
/doctor إذا كان يعرض معلومات تشغيل حساسة
وأي endpoint خاص لاحقًا

يمكن إبقاء health endpoint بسيط جدًا بدون بيانات حساسة إذا احتجناه.

6) AUDIT

سجّل فقط:
- authenticated owner yes/no
- safe user identifier/hash إذا احتجنا
- endpoint
- result

لا تسجل cookies أو tokens أو authorization headers.
