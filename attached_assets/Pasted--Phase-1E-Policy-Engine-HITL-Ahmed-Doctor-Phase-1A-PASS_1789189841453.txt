1. POLICY ENGINE

أنشئ تصنيف موحد لكل action/tool:

READ_SAFE
CREATE_REVERSIBLE
MODIFY_EXISTING
SENSITIVE_SIDE_EFFECT
HIGH_RISK

المعنى:

READ_SAFE
- search web
- search my files
- read metadata
→ execute automatically

CREATE_REVERSIBLE
- create draft
- create new file
- generate report
→ execute automatically + audit

MODIFY_EXISTING
- rename file
- move file
- edit existing document
→ configurable approval

SENSITIVE_SIDE_EFFECT
- send email
- delete file
- publish/post
→ explicit approval required

HIGH_RISK
- money/payment
- permission changes
- destructive bulk action
→ explicit approval always

2. TOOL METADATA

كل tool يجب أن يعرّف:
- tool_name
- risk_level
- requires_approval
- reversible
- external_side_effect
- data_scope

لا تعتمد على prompt فقط لتحديد الخطورة.

3. HITL

إذا الأداة تحتاج approval:
- لا تنفذها مباشرة
- أنشئ pending_action
- أرجع للمستخدم وصفًا مختصرًا لما سيحدث
- انتظر approve أو reject

لا يكفي approval text داخل prompt.
يجب أن تكون الموافقة server-side مرتبطة بـ:
- action_id
- session_id
- user identity
- expiration/status

4. POSTGRESQL

أضف جداول:

pending_actions
- action_id UUID PK
- session_id UUID
- run_id UUID
- tool_name TEXT
- risk_level TEXT
- arguments_json JSONB
- status TEXT
- created_at
- approved_at nullable
- rejected_at nullable
- executed_at nullable

audit_events
- event_id BIGSERIAL PK
- session_id UUID nullable
- run_id UUID nullable
- action_id UUID nullable
- event_type TEXT
- tool_name TEXT nullable
- status TEXT
- safe_metadata JSONB nullable
- previous_hash TEXT nullable
- event_hash TEXT
- created_at

اجعل audit log append-only في التطبيق.

استخدم hash chain بسيطة لكشف التعديل:
event_hash = hash(previous_hash + canonical event payload)

لا تدّعِ immutable storage.
سمّه tamper-evident audit log.

5. APPROVAL ENDPOINTS

أضف:
POST /actions/{action_id}/approve
POST /actions/{action_id}/reject

المستخدم الوحيد المصادق عليه فقط يستطيع استخدامها.

بعد approve:
- نفذ الأداة مرة واحدة فقط
- امنع duplicate execution
- سجّل audit event

بعد reject:
- لا تنفذ الأداة
- سجّل audit event

6. IDEMPOTENCY

كل action حساس لازم يكون idempotent.

إذا تكرر approve request:
- لا ينفذ مرتين

إذا restart حصل بعد approval:
- status من PostgreSQL يحدد هل نُفذ أم لا

7. PROMPT-INJECTION BOUNDARY

أضف قاعدة صريحة برمجية:
