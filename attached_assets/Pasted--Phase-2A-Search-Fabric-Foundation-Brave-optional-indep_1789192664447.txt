==================================================
GOAL
==================================================

الهدف ليس إضافة محركات كثيرة.

الهدف هو بناء Search Fabric صغير ومحايد للمزوّدين حول البحث الحالي، بحيث:

1. Tavily يظل مزود البحث الأساسي الحالي.
2. Brave يضاف كمزوّد اختياري يستخدم independent search index.
3. النظام يستطيع دمج نتائج أكثر من provider بدون ربط المنطق الأساسي بمزوّد واحد.
4. نقيس فعليًا هل Brave يضيف قيمة مقارنة بـTavily.
5. لا نجعل Brave جزءًا دائمًا من البحث إلا إذا أثبت benchmark فائدته.

لا تضف SearXNG أو أي search provider آخر في هذه المرحلة.

SearchProvider

- usage()

استخدم interface/protocol مناسب لهيكل Python الحالي.

لا تعيد كتابة Tavily implementation الموجود.

ضع Tavily adapter رفيعًا فوق التنفيذ الحالي في skill_tools.py أو المكان الأنسب بدون كسر السلوك الحالي.

Providers في Phase 2A:

1. Tavily
   - existing
   - configured
   - primary

2. Brave
   - optional
   - independent-index provider
   - may be NOT_CONFIGURED

لا تضف provider ثالث.

==================================================
6. SEARCH MODES
==================================================

احتفظ بالواجهة الحالية:

FAST
DEEP

FAST:

- Tavily فقط افتراضيًا.
- لا fan-out.
- لا Brave تلقائيًا.
- الهدف latency منخفضة.

DEEP:

لا يعني "شغّل كل providers".

استخدم selective provider routing.

إذا Tavily وحده كافٍ:
استخدم Tavily فقط.

إذا البحث يحتاج coverage إضافية أو independent second index،
وBrave status=READY:

شغّل:
Tavily + Brave

بشكل parallel قدر الإمكان.

إذا Brave=NOT_CONFIGURED:
DEEP يستمر عبر Tavily.

إذا Brave يفشل:
Tavily يستمر.

إذا Tavily يفشل وBrave READY:
Brave يمكنه الاستمرار.

لا تجعل failure من provider واحد يسقط البحث كله إذا provider آخر صالح.

الهدف:
quality per request
وليس maximum result count.

==================================================
8. URL NORMALIZATION
==================================================

قبل deduplication:

طبّق URL normalization آمن.

مثال:

- normalize hostname case
- normalize obvious default ports
- remove fragments عندما لا تغير هوية المورد
- remove common tracking parameters مثل:
  utm_*
  fbclid
  gclid

لكن:

لا تحذف query parameters بشكل أعمى.

بعض المواقع تستخدم query parameters كجزء أساسي من هوية الصفحة.

احتفظ بـ:

original_url
canonical_url

==================================================
9. DEDUPLICATION
==================================================

طبّق deduplication على مرحلتين.

PASS 1:
canonical URL exact/normalized dedupe

PASS 2:
near duplicate detection بشكل محافظ، مثل:
- same domain
- very similar title
- obvious syndicated duplicate

لا تعمل aggressive semantic dedupe قد يحذف مصادر مستقلة مختلفة.

إذا نفس الصفحة ظهرت من Tavily وBrave:

لا تعتبرها مصدرين مستقلين.

أرجع مصدرًا واحدًا مع:

found_by = ["tavily", "brave"]

==================================================
10. SOURCE INDEPENDENCE
==================================================

فرّق بين:

provider diversity

و

source diversity.

ظهور نفس Reuters URL من Tavily وBrave
لا يعني independent corroboration.

إذا عدة نتائج ترجع لنفس المصدر الأصلي أو نفس المقال syndicated:
لا تحسبها كعدة أدلة مستقلة.

احتفظ بالمعلومات اللازمة لمعرفة:

- provider الذي وجد النتيجة
- domain
- canonical URL
- source family إن أمكن بشكل محافظ

==================================================
11. FUSION
==================================================

ادمج النتائج باستخدام rank-based fusion.

ابدأ بـ:

RRF
Reciprocal Rank Fusion

أو equivalent rank-based method إذا كان هناك سبب تقني موثق.

اجعل RRF constant configurable.

لا تجمع Tavily raw score مع Brave raw score مباشرة.

Flow:

provider results
→ normalize
→ dedupe
→ rank fusion
→ quality adjustments
→ final source ranking

- source diversity
- duplicate/syndication penalty

لا تستخدم Gemini كـreranker لكل النتائج افتراضيًا.
